## Hardware Observation: Slow Asset Loading

The newly built game runs on physical hardware, but loading assets into the VDP
is noticeably slower than in earlier versions of the development environment
or firmware stack.

The leading hypothesis is that the slowdown occurs when MOS resolves a filename
passed as a string. Finding each requested file may have a substantial fixed
cost, and a historical MOS change may have made that lookup path slower. Because
the game loads many separate asset files, repeated pathname lookup could
dominate total startup time even if each file is read and transferred quickly.

Bulk reads from an already opened file and transmission to the VDP over UART are
not currently suspected to be the primary bottlenecks. This distinction has not
yet been measured, but it should guide the first inspection and test.

The investigation should distinguish among at least these stages, with the
first one receiving priority:

1. Resolving and opening each pathname supplied to MOS as a string.
2. Reading bytes after the file has already been found and opened.
3. Moving the data from eZ80 memory to the VDP over the command/UART interface.
4. VDP-side processing or buffer creation after receipt.

The emulator is useful for functional testing, but hardware timing is the
relevant measurement for this issue. Before changing code, the current loading
path and MOS API calls should be identified and timed or otherwise isolated.

## Asset-Loading Path Inspection

Reviewed the current MOS API documentation in `agon-docs/docs/mos/API.md` and
the active assembly path in `src/asm/files.asm`, `src/asm/mos_api.asm`, and
`src/asm/img_load.asm`. The generated asset-loading files and their Python
generator were then traced to locate the actual filename inventory.

### Relevant MOS API Behavior

- `mos_load` (`0x01`) accepts a zero-terminated pathname, destination address,
  and maximum size, and loads the complete file into memory.
- Starting with MOS 3.0, native MOS calls that accept path strings also support
  system-variable expansion and path-prefix resolution. MOS performs that
  handling automatically for native calls such as `mos_load` and `mos_fopen`.
- The lower-level `ffs_*` APIs call the underlying FatFS operations and require
  fully resolved pathnames. `ffs_fopen` and `ffs_fread` have been available
  since MOS 1.03.
- `mos_fopen` returns a MOS file handle. `mos_fread` can perform a block read
  from that handle, and `mos_getfil` can expose the underlying FatFS `FIL`
  object when direct FatFS operations are needed after a native MOS open.
- MOS 3.0 adds explicit path-resolution and directory-enumeration APIs, but
  using `ffs_fopen` still requires a pathname and therefore does not by itself
  eliminate FatFS directory lookup. It may, however, avoid MOS 3's additional
  native path-expansion/resolution layer when the game already has simple,
  fully resolved paths.
- The project's `src/asm/mos_api.asm` bindings were last updated in August 2023.
  They define the native file APIs through `mos_getkbmap` (`0x1E`) and FatFS
  APIs through `ffs_setcp` (`0xA5`), but do not yet define the MOS 3 path APIs
  or `ffs_flseek_p` (`0xA6`). The existing definitions are sufficient for a
  controlled `mos_load` versus `ffs_fopen`/`ffs_fread` experiment.

### Current Runtime Flow

The active executable includes `src/asm/images.asm`, not the alternative
`images_CMP.asm` file. Startup in `src/asm/wolf3d.asm` loads fonts, UI images,
BJ UI images, 3D panels, sprites, distance walls, and sound effects as separate
files.

`src/asm/img_load.asm` does not itself call MOS. It iterates a generated jump
table and calls one dedicated load routine per asset. It also redraws the
loading screen and prints the current filename between loads.

Each generated routine in `src/asm/images.asm` follows this pattern:

```asm
ld hl,F10_000
ld (cur_filename),hl
ld de,filedata
ld bc,65536
ld a,mos_load
RST.LIL 08h
```

After `mos_load` returns, the routine passes the known image dimensions, buffer
ID, and byte count to `vdu_load_img`.

`src/asm/files.asm` contains `vdu_load_buffer_from_file`, whose name obscures
an important boundary: it performs no filesystem operation. The file has
already been loaded into the `filedata` scratch area. This routine constructs a
VDP buffered-command stream and sends the command header plus asset bytes in a
single `RST.LIL $18` operation. The current protocol encodes the payload length
as 16 bits, limiting an individual transfer to 64 KiB.

### Current Assessment

The code structure strongly supports the repeated-path-lookup hypothesis. Even
if SD block reads and UART transfer are fast, 573 independent `mos_load` calls
impose 573 filename resolutions and file opens. Directories such as `panels/`
also contain hundreds of entries, so repeated FatFS directory scans may become
progressively expensive. MOS 3's automatic path expansion/resolution may add
another fixed or directory-search cost before the underlying file open.

Changing `mos_load` to `mos_fopen` plus `mos_fread` would separate open time
from read time for measurement, but it would not eliminate per-file opens.
Changing to `ffs_fopen` with the existing simple relative paths is a useful
controlled experiment for measuring the MOS path-resolution overhead, though
FatFS must still locate each named directory entry. Larger structural options
include enumerating directories once or packaging many assets into one or a
small number of container files so startup can use persistent handles and
sequential reads.

## Recovered Design Rationale and Possible Redesign

The current generated-loader architecture was chosen because the Agon does not
provide image metadata for raw RGBA2222 assets. Each `.rgba2` file is only a
sequence of one-byte pixels; it does not identify its width, height, pixel
format, buffer ID, or semantic role. The program must know those values before
it can create the corresponding VDP bitmap.

The generated assembly therefore performs several jobs at compile time:

- It acts as the asset manifest.
- It stores image dimensions and implied RGBA2222 format.
- It assigns stable VDP buffer IDs.
- It maps game/rendering concepts to those buffer IDs.
- It emits the pathname and unrolled load routine for every file.

This avoided writing runtime code to enumerate directories, sort files, retain
filenames or file objects, parse metadata, and construct lookup tables. The
tradeoff is a large amount of generated code and string data in the executable.
That has not yet exceeded the eZ80 memory budget, but it contributes directly
to the 573 independent pathname-based loads at startup.

### Candidate Runtime Architecture

A future design could initialize each asset class once:

1. Enumerate the class directory using the FatFS directory APIs.
2. Collect the matching entries.
3. Sort filenames in ASCII/numeric-compatible order so their order is stable.
4. Assign VDP buffer IDs sequentially at runtime.
5. Build the reverse lookup table dynamically.
6. Open, read, upload, and close each asset in that known order.

Keeping one open handle or `FIL` object for every asset is probably not viable:
MOS explicitly has a finite open-file limit (`EXIT_MAXOPENFILES`), and hundreds
of live FatFS objects would also consume memory. A runtime list of filenames or
compact asset descriptors is more realistic. Directory enumeration alone may
not remove the later pathname search needed by `f_open`, because the documented
API does not provide a way to convert a `FILINFO` directory result directly
into an open `FIL`. This needs verification against the MOS/FatFS
implementation before treating directory enumeration as a speed solution.

### Self-Describing RGBA2222 Files

A small project-defined header could turn raw `.rgba2` data into a
self-describing asset format. Candidate fields include:

- Magic value and format version.
- Width and height.
- Pixel format (`RGBA2222` initially).
- Payload byte length.
- Asset class/type and optional flags.
- Optional stable asset identifier or buffer-ID hint.

The build scripts would prepend this header, and the eZ80 loader would read and
validate it before issuing the VDP buffer upload and bitmap-create commands.
This would remove the need to emit width, height, size, and format in hundreds
of unrolled assembly routines.

Dynamic buffer IDs require a careful migration because buffer constants are
referenced broadly outside the generated loaders. A scan found hundreds of
distinct `BUF_*` references across rendering, font, UI, and other assembly
sources. The existing buffer numbering behaves like an internal ABI. A dynamic
scheme therefore still needs compact semantic-to-buffer mappings, predictable
class ranges, or another way for gameplay code to retrieve the assigned ID.

### Performance Implications

Per-file metadata headers reduce compiled code size and simplify generic
loading, but they do not by themselves remove the cost of opening hundreds of
separate pathname-based files. Directory enumeration may reduce some repeated
discovery work, but the documented APIs suggest each separate open may still
search the directory.

If startup speed remains the primary goal, the strongest structural option is
a packed asset container per class (or a single container) with one header/index
and concatenated payloads. That would allow one pathname resolution/open per
container followed by sequential reads through a persistent handle. The
per-image header proposal can be used inside such a container, so the metadata
work is compatible with a later packing step rather than being discarded.

## AgonVideo File Browser Reference

Inspected the existing file-management implementation exposed through the
project's local `AgonVideo` link. The remembered functionality exists, but it
is divided among several includes rather than being implemented in
`play.inc` alone.

### Memory Layout and API Bindings

`AgonVideo/src/asm/files.inc` assigns fixed absolute memory regions for:

- One browser `FIL` object.
- Browser state, including current path and page counters.
- One persistent FatFS `DIR` object.
- A table of 256 24-bit pointers to `FILINFO` records.
- A contiguous area for 256 complete `FILINFO` records.
- Separate browser and playback header buffers.
- One persistent playback `FIL` object and streaming data region.

The field addresses correspond directly to the structure offsets declared in
`AgonVideo/src/asm/mos_api.inc`. That include is only modestly newer than
AgonWolf3D's `src/asm/mos_api.asm`; its API function constants are the same. It
adds:

- `dir_struct_size = 46`.
- `filinfo_struct_size = 278` (`22 + 256`).
- Named FatFS attribute-bit positions (`AM_RDO`, `AM_HID`, `AM_SYS`, `AM_DIR`,
  and `AM_ARC`).
- An `FFSCALL` macro that preserves `IY` around `RST.LIL 08h`, which is useful
  because the browser frequently keeps a `FILINFO` pointer in `IY`.

It does not add the MOS 3 path-resolution calls; "updated" here primarily
means that it has the missing structure sizes, attribute definitions, and safer
call macro needed by the browser code.

### Directory Scan

The directory scan is implemented by `bf_get_dir` in
`AgonVideo/src/asm/browse.inc`, not by `play.inc`:

1. `ffs_getcwd` stores the current directory path.
2. `ffs_dopen` opens that directory into the persistent `DIR` object.
3. A loop calls `ffs_dread` once per directory entry.
4. Each accepted entry is stored as a complete 278-byte `FILINFO` record in a
   contiguous memory area.
5. A corresponding 24-bit pointer is appended to a separate pointer table.
6. Hidden and system entries are discarded.
7. Directories and playable files are tagged by placing ASCII `0` or `1` in the
   byte immediately before `filinfo_fname`, causing directories to sort before
   files.
8. After enumeration, the pointer table is sorted and the `DIR` is closed.

AgonVideo additionally verifies every non-directory candidate by opening it,
reading its WAV/AGM header, and closing it during the scan. An AgonWolf3D image
scanner would not want to duplicate that behavior merely to create the
inventory; metadata parsing can happen when each accepted asset is loaded.

### Sorting

`AgonVideo/src/asm/sort.inc` contains the sorting implementation.
`selection_sort_asc_filinfo` sorts the pointer table in place rather than
moving the large `FILINFO` records. It compares zero-terminated names by
unsigned ASCII values using `alpha_asc`. The artificial `0`/`1` byte described
above participates as the first comparison byte and groups directories ahead
of files.

This supplies exactly the useful pattern for AgonWolf3D: retain compact
pointers, keep the records stationary, and reorder only the pointer table.

### File Open and Streaming

`play.inc` consumes the sorted browser results. It asks
`bf_get_filinfo_from_pg_idx` in `input.inc` for the chosen `FILINFO`, then
`ps_open_wav`/`verify_wav` in `wav.inc` passes that record's leaf filename to
`ffs_fopen`. The resulting `FIL` remains open in `ps_fil_struct` while
`ps_read_sample` repeatedly calls `ffs_fread`, proving the persistent-handle
streaming pattern. Only the currently playing file is held open; AgonVideo does
not construct a table of hundreds of open handles.

### Reuse Limits for AgonWolf3D

The AgonVideo implementation is a reference design, not a drop-in asset
scanner:

- Its storage holds at most 256 `FILINFO` records and 256 pointers.
- The sort count is passed in the 8-bit `B` register, effectively limiting a
  sort operation to 255 entries.
- There is no bounds check before appending another record or pointer.
- AgonWolf3D currently has 408 files in `tgt/panels`; the generated classes are
  308 cube panels and 100 sprite panels. Even the cube class alone exceeds the
  existing sorter's count range.
- The other current directories are smaller: 9 distance walls, 11 top-level UI
  images, 20 BJ UI images, and 22 sound effects.

Adapting this design therefore requires either a wider-count sorting routine
and larger tables, class-specific filtering before collection, or multiple
bounded passes. The scanner also yields leaf filenames and metadata, not an
already-open file object, so each asset is still opened individually after the
scan.

## Preferred Direction: Packed Asset Stream

The preferred redesign is now to package the image assets into a single file
(or, if later justified, a very small number of class-specific pack files) and
stream its contents into VDP buffers through one persistent FatFS `FIL` object.

This directly addresses the dominant suspected startup cost:

- One pathname resolution and file open replaces hundreds of independent
  `mos_load` operations.
- Sequential `ffs_fread` calls reuse the already-open FatFS object, following
  the same proven pattern used by AgonVideo for continuous audio/video data.
- Directory scanning and sorting are unnecessary during normal startup.
- The 255/256-entry limitation in AgonVideo's browser design becomes irrelevant.
- Deployment becomes cleaner and faster because hundreds of small image files
  are replaced by one asset package.
- FAT directory layout and directory-entry search order no longer materially
  affect per-image load time.

The pack should begin with a versioned header and an index or sequence of
self-describing records. Each image record needs enough information to create
its VDP resource without generated per-image loader code. At minimum:

- A magic value and pack-format version.
- Asset identifier or deterministic semantic key.
- Asset class/type.
- VDP buffer ID or information needed to assign and record one dynamically.
- Width and height.
- Pixel format, initially RGBA2222.
- Payload length and either payload offset or an implied sequential position.
- Optional flags for compression or future formats.

Two layouts are plausible:

1. A complete index followed by all payloads. This supports validation and
   random access, and lets startup allocate IDs before reading pixel data.
2. A stream of `record header + payload` pairs. This is simpler and naturally
   supports a single sequential loading pass.

The current startup behavior favors the second layout unless gameplay later
needs random file-backed access. The loader can read one fixed-size record
header, validate it, read the declared payload into the existing scratch area,
upload it with the existing buffered VDP command, assign/store the resulting
buffer ID, and continue until the pack terminator or declared record count.

The existing VDP upload path uses a 16-bit payload length, so an individual
record must remain below 64 KiB or be uploaded in multiple VDP chunks. Current
images already obey the single-transfer limit, but the pack format should store
at least a 24- or 32-bit payload length so the on-disk format does not inherit
that implementation restriction.

This design can initially preserve today's stable buffer-ID allocation and
lookup semantics while removing pathname and metadata code. Dynamic buffer-ID
assignment can then be introduced separately, reducing the number of variables
changed in the first performance experiment.
