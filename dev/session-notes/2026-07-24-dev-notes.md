## AGNB Integration Audit

Reviewed the workflow guidance, eZ80 implementation notes, AGNB format
specification, loader API précis, image-load flow, and 2026-07-22 development
log in the requested order. Then inspected the Wolf3D build scripts, active
assembly include tree, image-generation pipeline, VDP routines, buffer-ID
conventions, application startup path, Git state, and the untracked
`src/asm/agnb.inc`.

The intended first integration scope is the RGBA2222 world-image families:
cubes, sprites, and distance walls. Fonts and UI images can remain on the
existing loose-file path initially. Sound effects must remain loose because
the AGNB 0.1 `AUDI` descriptor is deliberately unspecified.

This scope was confirmed before implementation. Sound effects are an intended
later AGNB use after the container's audio descriptor and finalization behavior
are specified. UI remains outside the first container because it currently
contains only a small number of files.

The font-loading follow-up confirmed that Wolf3D intentionally implements
proportional, coloured bitmap fonts at the application level. Each glyph is an
independent RGBA2222 bitmap with its own VDP buffer, dimensions, and vertical
offset; `font_bmp_plot` and `font_bmp_print` perform the proportional layout.
This is distinct from the VDP's native monochrome, monospaced, 256-glyph font
format. The existing glyph renderer will therefore be retained, and its
individual glyph images should eventually be packaged as ordinary AGNB `IMAG`
records. UI images should also move into AGNB eventually, but remain a lower
priority because there are comparatively few of them.

The principal integration findings are:

- `agnb.inc` is not yet included by the Wolf3D application.
- The loader depends on `FFSCALL`, `vdu_clear_buffer`, `vdu_load_buffer`, and
  `vdu_consolidate_buffer`, which are not present in the active Wolf3D
  dependency set.
- Its temporary traversal diagnostic depends on `DEBUG_WAITKEYPRESS`, which
  is also absent and should not be part of the production startup path.
- The existing Wolf3D routines already provide `umul24`, `vdu_buff_select`,
  `vdu_bmp_create`, `vdu_plot_bmp`, and `vdu_cls`.
- The loader's hard-coded 8 KiB scratch window at `$B7E000` conflicts directly
  with Wolf3D's runtime SRAM layout: `cell_status` begins at `$B7E000`,
  `cell_views` begins at `$B7E400`, and the sprite table begins at `$B7FC00`.
  Wolf3D must provide a different scratch pointer and capacity.
- Startup currently loads 308 cube images, 100 sprites, and 9 distance-wall
  images through generated loose-file routines after loading fonts and UI.
  The container call should replace only these three image-family passes in
  the first integration.
- Buffer IDs are assigned independently by several generators. The AGNB writer
  and assembly output must share one authoritative assignment and preserve
  every explicit ID unchanged.
- The current AGNB reader is the hardware-proven strict-layout implementation.
  Unknown-chunk seeking/skipping and general alignment helpers remain
  fail-closed stubs, so full extensible-reader conformance is a later step.
- The build deletes and recreates `tgt`; container generation must therefore
  occur after image generation and before assembly/deployment.
