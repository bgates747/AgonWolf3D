# Development Log — 2026-07-22

## Agon API review for the `.agnb` loader

Reviewed the official local Agon MOS, buffered-command, bitmap, enhanced-audio,
and VDU documentation against the focused slideshow-derived assembly harness
under `examples/agnb`. The resulting implementation précis is in
`docs/agnb-loader-agon-api-precis.md`.

The harness is intentionally broader than the minimum application and serves
as a test bed. The loader design should reuse relevant routines without
assuming every general-purpose helper belongs in the final path.

Principal findings:

- The loose-file baseline already uses the preferred modern pattern:
  `mos_fopen`, repeated 8 KiB `mos_fread` calls, and `mos_fclose`.
- In this slideshow harness, `filedata` is a deliberate fixed 8 KiB scratch
  window at `$B7E000`.
- Each read is appended as a VDP command-0 block; `vdu_load_img` then
  consolidates, selects, and creates the bitmap.
- The `.agnb` conversion should preserve that proven streaming machinery while
  moving the open/close boundary around the whole container and deriving buffer
  ID, image metadata, and exact transfer bounds from `BHDR`, `IMAG`, and `DATA`.
- The adopted `IMAG` order—width, height, format—matches the VDP
  bitmap-create payload exactly, and `BHDR` already matches the VDP's 16-bit
  buffer-ID byte order.
- A VDP block has a 65,535-byte maximum; buffers may contain multiple blocks.
  Bitmap data must be consolidated before bitmap creation, whereas future audio
  sample data may remain split across blocks.
- The generated loose-file table uses 15 bytes per image and its `MLT DE`
  indexing cannot uniquely address all 408 records. Container loading removes
  that table from the load path because every record contains its
  writer-specified buffer ID.

The recommended first vertical slice is a two-image `.agnb` container using
the existing MOS read loop and VDP helpers. After it renders on hardware, scale
to the 408-image benchmark before adding unknown-form seeking or audio.

The reusable loader itself must not hard-code the harness's `$B7E000` scratch
address or its 8 KiB size. It should operate on an application-provided 24-bit
pointer and capacity. Wolf3D already uses that onboard SRAM for map definitions
and may later load additional assets just in time, so it will choose a scratch
region suited to its own memory layout.

File-read size and VDP-upload size are separate. In ADL mode `mos_fread` accepts
a 24-bit count, whereas `RST 18h` and one VDP command-0 block use 16-bit lengths.
When a complete RIFF payload fits in the caller's scratch region, the loader may
read it with one MOS call and then subdivide it for VDP upload. Otherwise it
uses the same scratch region as a moving window over the payload.

A standalone application may place an uninitialized scratch label immediately
after its program and calculate capacity up to an application-chosen ceiling.
The conventional moslet boundary is not enforced by memory protection; whether
scratch may enter that region is a caller compatibility decision. The loader
must neither assume nor enforce that policy.

## Documentation discrepancy checklist

Cross-checked the format specification, Agon API precis, and image-load-flow
note on 2026-07-22. Work through these in order so implementation guidance does
not silently become a second specification:

- [x] **1. Make buffer ID `0xFFFF` invalid in the format specification.** The
  API precis correctly identifies `0xFFFF` as a VDP-reserved buffer ID and
  requires the loader to reject it. Resolved by defining the loader-side rule
  in the normative `BHDR` and reader requirements: reject the record before
  issuing any VDP command for it. This remains an implementation reminder for
  the loader rather than a new runtime buffer-allocation mechanism.
- [x] **2. Label the first vertical-slice loader as deliberately
  non-conforming or include required skip behavior.** The specification
  requires readers to skip unknown optional chunks safely and permits skipping
  unsupported record forms by their enclosing `LIST` size. Resolved by
  labeling the exact-structure first slice a restricted prototype and making
  its early-validation boundary explicit across the specification, API precis,
  and load-flow note: read and validate `BHDR`, `IMAG`, the `DATA` header and
  declared size, and all enclosing bounds before reading payload bytes or
  issuing any VDP command. Unknown-chunk and unsupported-form skipping remains
  required before calling the loader fully conforming; read-and-discard is an
  acceptable implementation and does not depend on MOS 3 seeking.
- [x] **3. Keep the proposed audio descriptor clearly non-normative.** The
  specification says `AUDI` is undefined, writers must not emit it, and readers
  must treat it as unsupported. Resolved by recording the production
  AgonJuekbox application specification as the existing implementation
  precedent while making clear that those conventions are not yet the generic
  `.agnb` contract. The applicable fields, validation, and loader behavior will
  be formalized in a later container-specification revision.
- [x] **4. Reconcile unconditional consolidation with the block strategy.**
  Resolved by adopting the known-working strategy as the loader design: every
  bounded read becomes one VDP block and every successfully uploaded image is
  consolidated before bitmap creation. The loader will not add a separate
  single-block path. One universal path handles images on either side of the
  65,535-byte block limit, avoids size-dependent branching, and keeps the
  assembly implementation smaller.
- [x] **5. Correct the phrase “five reordered `IMAG` bytes.”** Resolved while
  documenting the early-validation flow: the note now says to retain the five
  `IMAG` bytes. Their adopted `width`, `height`, `format` order permits direct
  transmission without reordering.
- [x] **6. State the supported image-format scope consistently.** Resolved by
  making version 0.1 and the initial loader RGBA2222-only. Writers emit format
  1, and readers reject another format before reading or uploading its `DATA`.
  Other formats are deferred and may never be needed. If added, they should
  reuse the same raw-byte transport and bitmap-finalization path; only layout
  and payload-size validation differ. RGBA8888 needs a four-byte-per-pixel
  factor, while mono/mask rows require whole-byte rounding.

- [x] **7. Keep buffer-ID ownership with the writer.** Resolved by removing the
  proposed sequential-ID display optimization from the design guidance. Every
  record must contain the ID selected by the writer. The reader validates and
  uses that exact value; it does not allocate, derive, auto-increment, or remap
  buffer IDs. Record order does not determine destination IDs.

- [ ] **8. Determine whether `FFSCALL` still needs to preserve `IY`.** The
  wrapper was introduced because some FatFS calls had undocumented behavior
  that destroyed `IY`, apparently in the emulator specifically; Tom reportedly
  corrected it shortly after it was raised. Test representative direct FatFS
  calls on current emulator and hardware MOS builds with a sentinel in `IY`.
  If both preserve it, replace `FFSCALL` uses with `MOSCALL` or reduce the macro
  to the ordinary call sequence. Avoiding `PUSH IY`/`POP IY` saves cycles, and
  index-register stack operations are more expensive than their general-purpose
  register equivalents.

The container test application now runs this open/read/validate/close sequence
before the inactive slideshow code. Three flag dumps showed Z set after open,
header validation, and close. A direct 12-byte RAM dump displayed:

```text
52 49 46 46  E0 EA 11 00  41 47 4E 42
 R  I  F  F                 A  G  N  B
```

The little-endian RIFF size is `0x0011EAE0`, or 1,174,240 bytes. Adding RIFF's
omitted first eight bytes gives 1,174,248 bytes, exactly matching the generated
physical `images.agnb`. The emulator therefore provides visible end-to-end

layout and that its FourCC and 32-bit size validation agree with the Python
writer. This is the first major milestone for the container reader.

## First image-load implementation checklist

The next work will proceed one item at a time, with review and manual direction
between items—especially when selecting or writing assembly math helpers.
`agnb_stream_data` is the form-agnostic transport primitive: it moves the
current `DATA` payload into the writer-specified VDP buffer and consolidates
that buffer, but does not interpret image, audio, or other form metadata.

- [x] **1. Read the first image record's complete metadata gate.** Validate
  `VERS`, `LIST BUFR`, `BHDR`, and `IMAG`, then read the `DATA` header without
  consuming payload bytes. Emulator inspection matched the first manifest
  entry exactly: bufferId 256, 16 by 35 pixels, RGBA2222, and a declared
  560-byte payload.
- [x] **2. Calculate the expected RGBA2222 payload size.** Adopted AgonVideo's
  tested `umul24` and added `agnb_calculate_image_data_size` for
  `width × height`. The helper returns the low 24-bit product. Its theoretical
  overflow threshold is 16,777,216 bytes/pixels—orders of magnitude larger
  than any conceivable Agon bitmap—so the loader deliberately avoids the
  additional machinery of a general 16-bit by 16-bit to 32-bit multiply.
- [x] **3. Complete the metadata validation gate.** Added
  `agnb_validate_image_data_size` immediately after the `DATA` header read. It
  requires the declared u32 high byte to be zero, compares the low 24 bits with
  the calculated `width × height`, and returns `agnb_error_data_size` before
  any payload read or VDP command if they differ.
- [x] **4. Prove the completed gate in the emulator.** The calculated and
  declared sizes both displayed as `30 02 00 00` for the first 16 by 35 image,
  and the record parser returned with Z set while retaining the file position
  at the first payload byte.
- [x] **5. Establish the generic VDP-buffer transport calls.** Reused the
  proven loose-harness implementations of `vdu_clear_buffer`,
  `vdu_load_buffer`, and `vdu_consolidate_buffer`, preserving their original
  order and code in the container's curated `includes.inc`.
- [x] **6. Implement bounded DATA streaming.** `agnb_stream_data` now clears
  the explicit writer-specified buffer, reads successive blocks no larger than
  the 8 KiB `agnb_io_buffer_size`, uploads every complete block, subtracts each
  transfer from a 24-bit remaining count, and requires the final logical file
  offset to equal the DATA payload end exactly. It deliberately stops before
  consolidation, which remains the next separate step.
- [x] **7. Consolidate the generic destination buffer.** After—and only
  after—the complete payload succeeds and the logical file position exactly
  matches the DATA end, `agnb_stream_data` now consolidates the explicit
  writer-specified `agnb_meta_bufferId`.
- [x] **8. Add image-specific finalization outside the primitive.** Added the
  proven `vdu_buff_select` and `vdu_bmp_create` routines in their original
  source order, then added `agnb_finalize_image` to select the retained
  bufferId and create a bitmap from the retained width, height, and format only
  after generic streaming and consolidation succeed.
- [x] **9. Render the first container-loaded image.** Added the deliberately
  inspectable 8 by 8 `00_000.png` as the first manifest record and displayed
  its bufferId 256 bitmap in the container harness. Its cyclic RGBA2222 rows
  use `C0 C3 CC CF F0 F3 FC FF`, and the source PNG round-trips through
  `agonutils` byte-for-byte.
- [x] **10. Finish the record and container traversal.** The loader consumes
  and validates every DATA padding byte, requires each record to end exactly
  at its enclosing `LIST` boundary, repeats the complete load/finalize sequence
  for all 250 records, and terminates only at the exact RIFF boundary. A
  temporary per-record display and keypress gate proved every image in order.

## Full-catalog hardware milestone

On 2026-07-23, completed and proved the entire 250-image container loader on
both the emulator and physical Agon hardware. `agnb_load_images` opens the
container once, validates the RIFF/version envelope, walks every strict
version-0.1 `LIST BUFR`, validates metadata before payload access, streams and
consolidates each explicit writer-specified buffer, creates every bitmap,
validates alignment and enclosing boundaries, and closes only after reaching
the exact RIFF end.

The generated application metadata now includes an `image_bufferIds` table
populated directly from the manifest. Slideshow navigation therefore selects
the exact writer-assigned bufferId for each image rather than deriving or
auto-incrementing IDs from record order.

For traversal diagnosis, each finalized image was temporarily cleared,
displayed, and held behind a keypress before the loader advanced. All 250
records displayed flawlessly in the emulator. The same stepped build was then
deployed alongside the loose harness to the physical SD card, where the user
confirmed that the complete container path works on real hardware.

The hardware container loader was substantially faster than the loose-file
harness. No formal timing was taken, so this is a qualitative result, but the
difference was clear enough to confirm the central performance premise:
opening and loading hundreds of individual files is suboptimal for large bulk
VDP-buffer loads, while one sequential container stream materially reduces
that overhead.

This is the major major milestone for the AGNB prototype: the format, Python
writer, manifest, assembly reader, generic bounded transport, image
finalization, full traversal, emulator behavior, and real-hardware behavior
now agree across the complete benchmark catalog.
