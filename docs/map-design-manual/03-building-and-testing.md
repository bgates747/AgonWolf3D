# 3. Building and Testing Maps

The master build driver is
[`build/scripts/build_00_all_the_things.py`](../../build/scripts/build_00_all_the_things.py).
Its flag block is intentionally controlled by commenting out unwanted `True`
assignments. Preserve that convention unless the Author decides to redesign
it.

## 3.1 Select the map source

One value determines which maps enter the application:

```python
map_src_dir = "src/mapmaker"
```

The master build discovers every `FF_R.map` file directly inside that
directory. It derives the complete floor and room set, rejects malformed
filenames, and fails on any sparse floor or per-floor room sequence before
stage 06 changes the database. There is no separately maintained floor list.

For a test suite, change only the directory. The active branch is presently
configured for the three-floor fixture:

```python
map_src_dir = "src/mapmaker/test_floors"
```

Restore `src/mapmaker` when the floor test is complete. The discovered floors
drive stages 06, 07, and 91c, so adding a correctly numbered map file is
sufficient to include it in the next map build.

## 3.2 Choose the correct starting stage

For changes only to `.map` definitions, begin at stage 06. The effective
map dependency path is:

```text
MapMaker FF_R.map files
        │
        ▼
06  import cells and tile metadata into tbl_06_maps
        │
        ▼
07  calculate per-cell/per-orientation visible panels
        │
        ▼
91c generate 8 KiB room images and floor/room filename tables
        │
        ▼
99  assemble wolf3d.bin
```

The current configured flag block also runs several inexpensive downstream
asset and metadata stages. That is intentional project workflow, even though
not all are strict map dependencies.

Start earlier when the upstream inputs changed:

| Change | Earliest relevant stage |
|---|---:|
| Map definitions only | 06 |
| Tile catalog or tile textures | 02 |
| View distance or projection geometry | 01 |
| Assembly only | 99 |

## 3.3 Run the build

From the project root:

```bash
.venv/bin/python -u build/scripts/build_00_all_the_things.py
```

Run it with visible progress output. Stage 07 can be quiet for a while because
it evaluates every usable cell and orientation. A successful three-floor,
two-room fixture build eventually reports all six stage-91c outputs:

```text
map_00_0
map_00_1
map_01_0
map_01_1
map_02_0
map_02_1
```

Stages 06 and 07 initialize their shared database tables only for the first
discovered floor, then accumulate the rest. The master build passes a
first-floor reset flag to both stages. Reintroducing an unconditional
per-floor table drop would leave only the final floor.

## 3.4 Expected outputs

For each map room, stage 91c writes:

```text
tgt/maps/map_FF_R.asm
tgt/maps/map_FF_R.bin
```

Stage 07 also recreates working/diagnostic composites under:

```text
build/maps/FF/masks
```

These PNGs can be numerous. They are gitignored, disposable build
intermediates rather than deployable map data.

The binary must be exactly 8,192 bytes. It contains the active cell table,
view masks, and initial sprite table described in
[Appendix B](appendix-b-map-build-format.md).

Stage 91c also replaces the `MAPS` section of
[`src/asm/autogenerated.asm`](../../src/asm/autogenerated.asm) with:

- the `floors` pointer table;
- one room-pointer table per floor; and
- MOS filenames for each generated room image.

Final assembly writes:

```text
tgt/wolf3d.bin
```

## 3.5 Sanity-check a multi-floor build

The build database should retain every selected floor. This bounded,
read-only check is useful after changing floor selection or importer logic:

```bash
.venv/bin/python - <<'PY'
import sqlite3

with sqlite3.connect("build/data/build.db") as connection:
    for table in ("tbl_06_maps", "tbl_07_render_panels"):
        rows = connection.execute(
            f"SELECT floor_num, COUNT(DISTINCT room_id), COUNT(*) "
            f"FROM {table} GROUP BY floor_num ORDER BY floor_num"
        ).fetchall()
        print(table, rows)
PY
```

Each complete 16×16 runtime map room contributes 256 rows to
`tbl_06_maps`. The exact stage-07 row count varies with geometry.

## 3.6 Deploy and run in the emulator

The canonical Wolf3D profile copies the current `tgt` tree and uses a
Wayland launcher:

```bash
cd /home/smith/Agon/mystuff/agon-dev-env
python3 scripts/setup_emulator.py wolf3d
scripts/run_emulator.sh wolf3d
```

Deployment must happen after the build. Otherwise the emulator continues to
use its previous map images even though local source files changed.

Current play-test controls are:

| Control | Action |
|---|---|
| `W` / `S` | Move forward / backward |
| `A` / `D` | Strafe left / right |
| Left / Right arrow | Turn counter-clockwise / clockwise |
| Up / Down arrow | Select next / previous owned weapon |
| Space | Fire the active weapon or use the knife |
| Escape | Exit to MOS |

There is no separate interaction key. Pickups and contact behaviors run when
the player attempts to enter their cell.

For a map test, verify:

1. The application starts in the intended floor-0 room-0 start cell.
2. Wall themes and landmarks match the planned map room.
3. Pickups disappear and remain gone after leaving and returning.
4. Enemies and mutable props retain their state after backtracking.
5. Every room link works forward, immediately backward, after rotation, and
   while backing through the arrival door.
6. No transition places the player in an inaccessible cell.

Floor-switch testing will be added to this sequence when elevator handling is
implemented.

With the Agon SD card mounted at the canonical path:


The script replaces only:


## 3.8 Common failures

| Symptom | Likely cause |
|---|---|
| Map validation rejects a tile | An inactive, unknown, Clear-generated ID 1, or runtime-only ID 60 remains in the map |
| Map validation rejects the source set | Invalid filename/structure, sparse IDs, missing start, bad link topology, or too many sprites |
| Only the final floor is generated | A stage-06 or stage-07 table was reset for every floor |
| New maps build but emulator shows old maps | The rebuilt `tgt` tree was not redeployed |
| Runtime start/transition failure after a validated build | A deployed room file was replaced or corrupted, or validation/runtime behavior regressed |
