# Appendix B: MapMaker and Build Formats

This appendix follows one authored cell from MapMaker to the external 8 KiB
room image loaded by MOS.

## B.1 MapMaker `.map` file

A normal Wolf3D map contains:

| Records | Bytes | Meaning |
|---:|---:|---|
| 1 | 5 | Maximum X index, normally 14 |
| 1 | 5 | Maximum Y index, normally 14 |
| 1 | 5 | Standard bank count, normally 5 |
| 1 | 5 | Custom bank count, normally 0 |
| 225 | 1,125 | 15×15 object IDs |

With no custom banks:

```text
(4 + 225) × 5 = 1,145 bytes
```

For the small nonnegative values used by Wolf3D, each BBC BASIC numeric record
is the integer in little-endian form padded to five bytes.

MapMaker stores cells as `the_map%(YCORD%,XCORD%)`. Its save/load routines
walk the first array dimension outside the second, so the payload is semantic
Y-major, X-minor. Stage 06 reads it in the same order; there is no transpose.

Optional custom-bank records can follow the cells. Wolf3D ignores them and
does not support custom MapMaker zones as a game asset source.

## B.2 What stage 06 assumes

[`build_06_map_import_mapmaker.py`](../../build/scripts/build_06_map_import_mapmaker.py)
does not validate the four header fields. It:

1. discards the header;
2. reads exactly 225 five-byte object records;
3. assumes configured dimensions of 16×16;
4. inserts the authored values at coordinates 0–14;
5. inserts the active `special = "outer"` object at `x = 15` or `y = 15`;
6. joins every object to active `tbl_02_tiles` metadata; and
7. converts the stored object ID of ordinary non-wall, non-door, non-trigger
   cells to floor object 29 while retaining their original render and sprite
   metadata.

That last step means the runtime `map_obj_id` of a health pack is normally 29.
Its identity survives through its sprite image/type ordinal and sprite-table
record.

The map-build validation gate checks file structure, object membership,
floor/room density, starts, link topology, and sprite capacity before stage
06. Discovery returns an ordered mapping of every floor and room file, and the
low-level importer iterates that mapping directly. It assumes the selected
source set has already passed validation rather than searching a fixed range
or repeating those checks internally.

It also assumes the catalog supplies an active `special = "outer"` object and
an active `render_type = "floor"` object. Both are selected with an unchecked
first-row lookup, so either a missing definition or duplicates can fail or
silently change the result.

## B.3 Map-related database stages

```text
tiles.txt
   │
   └── stage 02 ──> tbl_02_tiles + qry_02_img_idx

FF_R.map
   │
   └── stage 06 ──> tbl_06_maps
                          │
projection polygons ─────┤
                          ▼
                    stage 07
                          │
                          └──> tbl_07_render_panels
                                      │
                                      ▼
                                    stage 91c
```

### Stage 02

Imports the tile catalog, assigns per-render-type image indices, and creates
source thumbnails used by transformed image generation. It is needed when
tile definitions or source textures change, not for ordinary cell placement.

### Stage 06

Produces one database row for each of 256 runtime cells. The master build
resets the shared table on the first selected floor and accumulates all later
floors.

### Stage 07

Crosses map cells with four orientations and the projected polygon table. It
renders color-coded candidate panels and retains those that remain visibly
significant after occlusion. The result is the per-view panel set in
`tbl_07_render_panels`.

The SQL views span all imported floors and are recreated on each floor call;
processing is floor-filtered, so the result is correct but not maximally
efficient.

The stage's progress message is tied to cell 0 being a viable viewpoint.
Because cell 0 is normally a wall, a long valid run can appear silent.

Stage 07 recreates a PNG composite for every processed viewpoint beneath
`build/maps/FF/masks`. These numerous files are gitignored diagnostic/working
artifacts and may be deleted between builds.

### Stage 91c

Generates:

```text
tgt/maps/map_FF_R.asm
tgt/maps/map_FF_R.bin
```

and replaces the `MAPS` section of
[`autogenerated.asm`](../../src/asm/autogenerated.asm).

## B.4 Compiled cell record

Each of the 256 cells becomes four bytes:

| Offset | Assembly symbol | Meaning |
|---:|---|---|
| 0 | `map_type_status` | Six flags and two-bit render type |
| 1 | `map_img_idx` | Cube image index or sprite behavior/render ordinal |
| 2 | `map_obj_id` | Logical or underlying cell object |
| 3 | `map_sprite_id` | Room-local sprite index or 255 |

Status byte:

```text
bit 7  is_door
bit 6  is_wall
bit 5  is_trigger
bit 4  is_blocking
bit 3  is_start
bit 2  is_to_room
bits 1–0  render type
```

The render values are currently:

```text
0 cube
1 floor
2 null
3 sprite
```

UI start object 28 is deliberately encoded as floor plus the start bit.

## B.5 Visibility records

The engine supports up to 48 projected panels. Stage 07/91c writes a 48-bit,
six-byte mask for every:

- cell 0–255; and
- orientation north, east, south, west.

This is:

```text
256 cells × 4 orientations × 6 bytes = 6,144 bytes
```

The masks drive both rendering and enemy awareness.

## B.6 Sprite IDs

Stage 91c assigns room-local sprite IDs in ascending cell-ID order. Every
database row whose render type is `sprite` receives the next ID.

The generated room image reserves only 64 records. Stage 91c does not enforce
that ceiling internally; it relies on the earlier map-validation gate. If
stage 91c is invoked while bypassing validation, an object count above 64
produces IDs that runtime sprite initialization writes beyond its table.

## B.7 Exact 8 KiB room image

| File offset | Runtime address | Size | Contents |
|---:|---:|---:|---|
| `$0000` | `$B7E000` | 1,024 | 256 four-byte cells |
| `$0400` | `$B7E400` | 6,144 | View masks |
| `$1C00` | `$B7FC00` | 1,024 | 64 blank 16-byte sprite records |
| | | **8,192** | |

The source `.asm` representation is diagnostic. The `.bin` is the external
file that `map_load` asks MOS to load.

## B.8 Generated floor and filename tables

Stage 91c queries the floor/room pairs that survived stage 06 and produces:

```asm
floors:
    dl floor_00
    dl floor_01

floor_00:
    dl room_00_0
    dl room_00_1

room_00_0:
    db "maps/map_00_0.bin",0
```

Runtime lookup uses `cur_floor` and `cur_room` as direct three-byte pointer
indices. No count or bounds metadata is generated. Dense zero-based IDs are
therefore mandatory.

Stage 91c also uses an unchecked first-row lookup for the active
`special = "start"` definition. Stage 07 presently performs similar lookups
for the active outer, null-cell, and start definitions even where the fetched
IDs are not subsequently used.

Stage 91c currently does not remove stale map files it generated during an
earlier configuration. Those unreferenced files are harmless at runtime but
are copied into deployments. Cleanup should eventually remove only stale
outputs owned by stage 91c.
