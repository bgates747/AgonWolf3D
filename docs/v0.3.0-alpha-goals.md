# AgonWolf3D v0.3.0alpha Goals

Status: **DRAFT**

This is the working scope for the next release. The Author's agenda is
authoritative; Codex recommendations remain optional until the Author promotes
them. Implementation history belongs in the development logs.

Task numbers are stable references. New tasks receive new numbers rather than
causing existing tasks to be renumbered.

## Starting baseline

Version 0.2.0.alpha established:

- container files for all current bitmap and sound-effect assets;
- at least a tenfold reduction in asset-loading time;
- a substantially smaller executable;
- animated loading progress;
- proportional ITC Honda font support;
- successful emulator and physical-hardware validation; and
- a reproducible external development/emulator environment.

Development continues on `dev`; `main` remains the release branch.

## Explicitly deferred unless promoted

- Sound-format extensions beyond the current AGNB 0.2 PCM records.
- Major engine rewrites.
- Expanding MapMaker rooms from 15×15 to a true 16×16. The current authored
  maps are padded to the engine's natural 16×16 representation, and the
  limitation causes no material gameplay problem.
- Original-style saved games. The eventual versioned save format must include
  the durable variables in `vars.asm`, the active mutable 8 KiB room image,
  and every valid cached room image needed for a faithful restore.
- Work on Nurples.
- Broad optimization based only on theoretical executable-size savings.

## The Author's agenda

- [x] **22.** Verify and correct room-to-room movement within a floor.

  A room is one complete 15×15 MapMaker definition, not merely an enclosed
  architectural space. Destination-door objects 30–39 select rooms 0–9.
  `change_room` continues to save and restore each room's mutable 8 KiB image.
  The new `room_transition_depart` path preserves the entry vector so the
  player can proceed, turn around, or back through the arrival door without
  being placed in an invalid cell. The changes touched `player.asm`,
  `maps.asm`, and transition state later centralized in `vars.asm`.

- [x] **23.** Validate the room-transition repair with the simplified maps in
  `src/mapmaker/test_rooms`, then restore and rebuild the standard maps.
  Forward traversal, immediate reversal, turning around, and backing through
  the transition were tested successfully in the emulator.

- [x] **24.** Stop tracking generated map-render masks. Removed the previously
  committed PNG masks and ignored `build/maps` so a build no longer creates
  thousands of distracting source-control changes.

- [x] **25.** Establish a dedicated game-variable area as save-game
  groundwork. `vars.asm` now separates durable state, runtime-only workspace,
  and explicitly unsaved debug state. Durable state includes player and room
  state, random seeds, sprite bookkeeping, BJ's health image, and
  room-transition state. Full saves will additionally require mutable room
  images.

- [x] **26.** Consolidate final-assembly generated code in
  `autogenerated.asm`. The master build and individual generators now replace
  isolated `IMAGES`, `MAPS`, `POLYS`, `FONT`, `UI`, `UI_BJ`, and `SFX`
  sections through marker-safe atomic updates. The former generated assembly
  files and generated tail of `maps.asm` were removed. A clean full build and
  emulator launch succeeded.

- [ ] **27.** Implement movement to the next floor.

  A floor is a collection of connected MapMaker rooms. Before enabling more
  than floor 0, the map-import and render-panel build stages were changed to
  initialize their shared tables once and accumulate all selected floors.
  The test build now retains all six rooms across floors 0–2. Runtime work
  must still define how floor transitions reset or preserve the floor-local
  `room_flags` and ten mutable-room caches. Build discovery now guarantees
  dense zero-based floor and room IDs before generating the runtime's
  direct-indexed tables. The three-floor fixture, terminology, MapMaker format
  discoveries, and remaining implementation dependencies are documented in the
  [map design and runtime manual](map-design-manual/README.md); fixture-specific
  construction details remain in
  [`src/mapmaker/test_floors/README.md`](../src/mapmaker/test_floors/README.md).

- [ ] **28.** Separate the responsibilities currently combined in
  `maps.asm`.

  Keep map representation, coordinate lookup, room-file loading, and sprite
  initialization in `maps.asm`. Move navigation policy and mutable room
  caching—especially `room_transition_depart`, `change_room`, `room_flags`,
  and `room_dat_lut`—to a dedicated `room_transition.asm`. Persistent state
  remains in `vars.asm`; generated floor and room tables remain in the `MAPS`
  section of `autogenerated.asm`.

- [ ] **29.** Implement gold and silver keys and key-locked doors using the
  original Wolf3D division of responsibility.

  Keys unlock ordinary doors, not elevators or floor transitions. Map design
  may nevertheless place a locked door on the route to the exit. Key
  ownership is durable floor-wide state: it survives room changes, resets on
  a new floor, and participates in saved games. Collected keys and door state
  must persist in their owning rooms' mutable images, and denied access needs
  clear player feedback.

  Original behavior references:
  [id Software's door and key-checking code](https://raw.githubusercontent.com/id-Software/wolf3d/master/WOLFSRC/WL_ACT1.C),
  [id Software's player and elevator-use code](https://raw.githubusercontent.com/id-Software/wolf3d/master/WOLFSRC/WL_AGENT.C),
  and [The Wolf Front's key and level-placement summary](https://wolfenstein3d.nl/in-game-items/).

- [ ] **30.** Enforce the 64-sprite limit during map generation.

  Count every sprite-rendered cell in each map room, including scenery,
  pickups, enemies, and deliberately authored corpses. Fail the build with a
  clear floor, room, actual-count, and maximum-count error when the total
  exceeds the 64 records reserved in the runtime room image. Current corpse
  and explosion transformations reuse existing records, so they do not
  require additional capacity.

- [x] **31.** Enforce dense floor and map-room IDs during map generation.

  Stage 06 now discovers every direct `FF_R.map` child of `map_src_dir`,
  rejects malformed filenames, and verifies that floors and each floor's
  rooms independently form dense zero-based sequences. The resulting ordered
  map set drives stages 06, 07, and 91c; the separate `floor_nums`
  configuration was removed. Sparse IDs fail before database mutation with
  the found and missing IDs.

- [ ] **32.** Clear room-transition state when restarting the player after
  death.

  `plyr_restart` must disarm `room_transition_active` before placing the
  player at room 0's floor start. Otherwise, death while standing on a
  reciprocal arrival cell can preserve a stale entry vector and make a later
  reverse-direction movement call `change_room` using the ordinary start cell
  as though it were a room link. Test death and subsequent movement from both
  ordinary cells and an arrival-door cell.

- [ ] **33.** Enforce the floor-start invariant during map generation.

  Require room 0 of every selected floor to contain exactly one start marker.
  Fail the build with the floor, room, and observed count when the marker is
  missing or duplicated, preventing `get_floor_start` from performing an
  unbounded search or silently selecting an unintended start.

- [ ] **34.** Validate room-link topology during map generation.

  For every room-link object 30–39, require the named destination room to
  exist and to contain exactly one reciprocal `30 + source_room` object.
  Reject self-links, duplicate links from one room to the same destination,
  missing reciprocals, duplicate reciprocals, and destinations outside the
  generated floor. Report the floor, source room, destination room, and
  failing object IDs before generating runtime pointer tables or room images.

- [ ] **38.** Evaluate ray casting and BSP-based spatial-query architectures
  for future rendering and gameplay.

  John Carmack wrote in the original Wolf3D release notes:

  > Some coding comments in retrospect:
  >
  > The ray casting refresh architecture is still reasonably appropriate for
  > the game. A BSP based texture mapper could go faster, but ray casting was
  > a lot simpler to do at the time.

  Source: id Software's `WOLFSRC/README/RELEASE.TXT`, available locally at
  `/home/smith/Agon/id/wolf3d/WOLFSRC/README/RELEASE.TXT`.

  Think through whether an ESP32-side real-time renderer should retain
  Wolf3D-style ray casting or use a BSP-based texture mapper. Also evaluate
  whether BSP organization could accelerate eZ80-side gameplay queries such
  as line of sight and blast propagation, rather than assuming every such
  query must use grid ray casting. Keep the two processor roles distinct:
  rendering architecture on the ESP32 VDP and authoritative gameplay/spatial
  queries on the eZ80 may reasonably reach different conclusions.

  - [ ] **38.1.** Revisit enemy awareness, movement, attacks, and their coupling
  to the precomputed player-view system.

  The current behavior is not limited strictly to the scene facing the
  player, but it is still player-visibility driven. `main_loop` in
  `wolf3d.asm` calls `sprites_see_plyr` before player input and rendering.
  `sprites_see_plyr` in `sprites.asm` reads the `cell_views` masks for the
  player's current cell and deliberately loops `see_orientation` through all
  four cardinal orientations. A guard behind the player can therefore remain
  active even though `render_scene` does not draw him in the current view.

  Only sprites encountered in the union of those four precomputed views
  receive `sp_see` through `sprite_set_pointer` and
  `do_sprite_behavior`. The German-trooper and SS-guard `@see` handlers set
  `sprite_trigger_see`, then enter their `@move`/`@shoot` behavior. That flag
  remembers that the player was noticed, but does not independently schedule
  the enemy: if a guard is no longer present in a current `cell_views` mask,
  no behavior routine is called and the guard effectively freezes.

  `sprite_shoot` performs no independent obstruction or line-of-sight trace.
  It permits a shot when the enemy and player share either X or Y, relying on
  the earlier visibility-mask selection to imply a clear shot. Enemy movement
  is presently `sprite_move_random`, not pursuit, and `view_distance` in
  `render.asm` also bounds the precomputed view system used for awareness.

  Discuss and design the intended replacement before changing this code.
  Distinguish local tile collision from the spatial queries needed for enemy
  sight, persistent pursuit, weapon traces, doors, and attacks. Consider
  whether eZ80-side grid raycasting, a cheaper line-of-sight routine, an
  independently updated active-enemy set, or some combination best serves
  both this engine and the Author's longer-term real-time 2.5D goals. Preserve
  reproducible cases for enemies ahead, behind, beyond view distance, and
  separated from the player by walls or doors.

  - [ ] **38.2.** Implement line-of-sight splash damage from exploding barrels
  to the player and damageable sprites.

  `BARREL:@kill` and `RADIOACTIVE_BARREL:@kill` in `sprites.asm` currently
  play the explosion sound, replace their existing sprite record with
  `OBJ_ID_EXPLOSION` through `sprite_spawn`, and start its animation timer.
  `EXPLOSION:@see` only advances that animation and removes the sprite.
  `EXPLOSION:@use` applies lethal contact damage to the player, but no blast
  is propagated when the barrel actually explodes.

  At the moment of barrel destruction, use the barrel's `sprite_x` and
  `sprite_y` as the origin of a bounded grid/ray query. Damage the player and
  eligible sprite records only when the blast has a valid line of sight;
  walls and closed doors must block it. Settle the blast radius, ray coverage,
  diagonal/corner behavior, distance falloff, and whether ordinary and
  radioactive barrels have different damage profiles. An entity must receive
  damage at most once per explosion.

  Do not route environmental damage through player-shot state merely because
  enemy `@hurt` handlers currently consume `plyr_shot_damage` and modify
  `plyr_shot_status`. Introduce or design a generalized damage path that can
  identify damage amount and source, call `plyr_sub_health` for the player,
  invoke the appropriate sprite hurt/kill behavior, and support barrel chain
  reactions without recursively corrupting `iy`, the active sprite-table
  traversal, or explosion state. Decide explicitly whether blast effects stop
  at the active map-room boundary.

  Treat this as an early practical consumer of the spatial-query work in task
  38. Test unobstructed targets at several distances, targets behind walls and
  doors, diagonal corner cases, player self-damage, multiple targets, and
  chained barrel explosions.

- [ ] **39.** Rebalance guard health and player weapon damage while
  preserving the intended burst-versus-ammunition tradeoff.

  The current `plyr_set_weapon_parameters` values in `player.asm` assign 30
  damage to a one-round pistol burst, 80 damage to a four-round machine-gun
  burst, and 120 damage to an eight-round Gatling burst. The corresponding
  shooting routines consume 1, 4, and 8 ammunition. Thus rapid-fire weapons
  deliberately do less nominal damage per cartridge in exchange for a larger,
  more reliable amount of damage from one trigger pull; the pistol should
  remain the ammunition-efficient choice when the player accepts needing more
  shots.

  Current enemy health is 75 for `GERMAN_TROOPER` and 100 for `SS_GUARD` in
  `sprites.asm`, which makes both feel too durable under the present damage
  calculation. Before merely reducing those values, inspect `plyr_shoot`:
  it obtains one random byte and performs a bitwise `AND` with
  `plyr_wpn_damage`, negating the result into `plyr_shot_damage`. This is not a
  smooth fractional modifier. For example, a mask of 80 can produce only the
  bit combinations represented by `0x50`, including zero damage, rather than
  a useful continuous damage range. One damage result is then applied to the
  single sprite struck by `plyr_move_bullet`; individual rounds in a
  machine-gun or Gatling burst are not simulated separately.

  Decide whether the right correction is lower guard health, a better
  randomized burst-damage calculation, or both. Define target outcomes before
  tuning: expected pistol shots per guard, probability that each rapid-fire
  burst kills each guard class, damage and ammunition efficiency per burst,
  acceptable zero/low-damage outcomes, and the knife's place in the same
  scale. Test the actual distribution rather than only maximum damage values,
  and keep the weapon comments, UI expectations, and eventual generalized
  damage path from task 38.2 consistent with the chosen model.
