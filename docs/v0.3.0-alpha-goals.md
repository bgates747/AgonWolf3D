# AgonWolf3D v0.3.0alpha Goals

Status: **DRAFT**

This document is the working scope for the next AgonWolf3D release. Goals
remain proposals until reviewed and accepted. Implementation details and
chronological work belong in the development log.

## Starting baseline

Version 0.2.0.alpha established:

- AGNB containers for all current bitmap and sound-effect assets;
- at least a tenfold reduction in asset-loading time;
- a substantially smaller `wolf3d.bin`;
- animated image and sound loading progress;
- proportional ITC Honda font support;
- successful emulator and physical-hardware validation; and
- a reproducible external development/emulator environment.

Development continues on `dev`; `main` remains the release branch.

## Codex recommendations

Everything in this section is a non-binding Codex recommendation for
discussion. These items are not the Author's agenda and are not release
requirements unless the Author explicitly promotes them.

### Cleanup and maintainability

- [ ] Review obsolete assembly routines, generated tables, includes, and VDP
  helpers without turning size reduction into a speculative rewrite.
- [ ] Remove confirmed dead code in small, independently tested changes.
- [ ] Continue separating application policy from reusable APIs.
- [ ] Review the reduced map-only build path and retain a fast, dependable
  edit/build/test loop.

### Presentation and release polish

- [ ] Review startup, loading, error, and exit presentation for consistency.
- [ ] Review visible version naming and settle the canonical spelling for
  `v0.3.0alpha`.
- [ ] Identify small visual or usability improvements appropriate to an alpha
  release.

### Gameplay and map development

- [ ] Continue play-testing the opening map after the additional health and
  ammunition pickups.
- [ ] Record specific balance, navigation, encounter, or map-tooling goals
  before treating them as release requirements.

### Reliability

- [ ] Preserve clean startup, gameplay, sound playback, and exit behavior in
  the emulator and on physical hardware.
- [ ] Keep failures in previously running AgonJukebox/VDP state tracked as an
  AgonVideo concern unless Wolf3D can reproduce them after a clean boot.

## Explicitly deferred unless promoted

- Sound-format extensions beyond the current AGNB 0.2 PCM records.
- Major engine rewrites.
- Expanding MapMaker and authored room definitions from 15×15 to a true 16×16.
  Although 16×16 is the natural fit for the engine's compact coordinate
  representation, the current limitation causes no material gameplay problem
  and is only a possible long-term goal.
- Add original-style saved games as a long-term goal. A save file should
  preserve enough state to resume play faithfully, including the current
  floor and room, player position and orientation, health, lives, score,
  weapons and ammunition, room-visited state, and all mutable state for every
  room that must survive a reload. The eventual design should build on the
  existing 8 KiB active-room image and per-room RAM caches, while defining a
  versioned on-disk format that can be validated before restoring it. This is
  not a v0.3.0alpha requirement.
- Work on Nurples.
- Broad optimization based only on theoretical executable-size savings.

## The Author's agenda

This section is authoritative. Add and revise items here as the Author defines
the actual v0.3.0alpha scope. The Author's agenda takes precedence over the
Codex recommendations above.

- [ ] Verify and correct room-to-room movement. In game terminology, a “room”
  is one complete map definition held in a single MapMaker instance, not
  merely an enclosed architectural space. The first v0.3.0alpha task is to
  ensure transitions between those separate room definitions work properly.

- [ ] Implement movement through a floor's connected rooms. A “floor” is a
  collection of MapMaker room definitions, rather than a single map.

  - Special destination-door tiles link the rooms. The current tile catalog
    defines object IDs 30–39 as `DOOR TO ROOM 0` through `DOOR TO ROOM 9`;
    therefore the selected tile itself identifies the destination room.
  - These links are represented differently from ordinary doors: they are
    blocking trigger cubes with `special = "to room"`. The build encodes that
    property in the generated map-type status byte.
  - On activation, load the destination room's definition into the designated
    map area in RAM, then locate its corresponding door cube.
  - Place the player in the valid map cell one tile away from that destination
    door. Recover or implement the intended placement rule carefully: any map
    cell has eight possible neighbors when the four diagonals are included.
    The arrival cell and facing direction must be derived consistently rather
    than assumed to lie on one fixed side.
  - Preserve the design constraint that a room on a given floor may contain
    no more than one pair of these linked-room doors. Confirm the precise
    meaning and enforcement point of “door pair” while tracing the existing
    runtime logic.
  - Reuse the build's existing floor/room organization. Map import currently
    accepts room IDs 0–9, and map generation already emits individual
    `maps/map_FF_R.bin` room files plus per-floor room-pointer and filename
    tables.
  - Before changing runtime code, trace the generated room-table layout, the
    designated map RAM address, trigger handling, current room loader, and any
    surviving destination-door or arrival-position logic.

  Build-pipeline trace:

  - `build_00_all_the_things.py` establishes the map dimensions as 16×16 and
    currently selects only floor 0 with `floor_nums = list(range(1))`. For a
    map-only rebuild it begins at stage 06, calls stages 06 and 07 once for
    every selected floor, later calls stage 91c once with the complete floor
    list, and finally assembles the application at stage 99. Several unrelated
    asset stages currently remain enabled after the map-only starting point;
    they are not part of the floor/room data path.

  - `build_02_fetch_tiles.py` is an upstream dependency rather than part of
    the usual map-only rebuild. It imports `src/mapmaker/tiles.txt` into
    `tbl_02_tiles` and creates the image-index view used downstream. The tile
    catalog is where object IDs 30–39 acquire their `DOOR TO ROOM 0` through
    `DOOR TO ROOM 9` meanings and `special = "to room"` status.

  - `build_06_map_import_mapmaker.py` is the map ingestion stage. It recreates
    `tbl_06_maps`, searches room IDs 0–9 for files named `FF_R.map`, discards
    the MapMaker header, and imports the authored 15×15 cells as five-byte
    object IDs. It pads the last row and column with the configured outer-wall
    object to produce the engine's 16×16, 256-cell map. It then joins each
    object ID to `tbl_02_tiles`, copying collision, trigger, render, and
    `special` metadata into every cell. Finally, ordinary non-wall,
    non-door, non-trigger cells have their stored object ID replaced by the
    default floor object, while their previously copied metadata remains
    available.

    Important multi-floor conflict: `import_mapmaker()` calls
    `make_tbl_06_maps()` for every floor, and that function drops the entire
    table. Since the master script invokes `import_mapmaker()` separately for
    each selected floor, enabling multiple floors would retain only the last
    imported floor. Table initialization must be moved outside the per-floor
    operation, or the importer must ingest all requested floors in one call.

  - `build_07_polys_make_map_panels.py` computes the preselected polygon masks
    used to render every viable player view. It expands each imported cell
    across four orientations, joins the surrounding 3D polygons using
    orientation-specific 16×16 wrapped coordinates, and uses color-coded
    raster images to determine which panels remain visible after occlusion.
    It includes walkable cells, ordinary doors, and `special = "to room"`
    trigger cells as possible viewpoints. Its results are stored in
    `tbl_07_render_panels`; diagnostic mask images are written beneath
    `build/maps/FF/masks`.

    Important multi-floor conflict: this stage also drops and recreates its
    shared results table on every per-floor call. Its SQL views are not
    restricted to the `floor_num` argument, although final processing is.
    This happens to work for the present single-floor build but needs
    restructuring before generating several floors reliably.

  - `build_91c_asm_map_masks.py` converts the database representation into the
    runtime room files. For every selected floor and existing room ID 0–9, it
    writes `tgt/maps/map_FF_R.bin` (and a readable generated `.asm` companion).
    Each binary begins with 256 four-byte cell records: status flags, image
    index, object ID, and room-local sprite ID. The status byte includes
    ordinary-door, wall, trigger, blocking, start, and linked-room bits.
    Six visibility-mask bytes are emitted for each cell/orientation view,
    followed by a 1,024-byte initialized sprite table.

    The generated room binary is laid out for loading at `0xB7E000`: cell
    records begin there and view masks begin at `0xB7E400`. The same script
    rewrites the generated portion of `src/asm/maps.asm` with the start object
    ID, a `floors` pointer table, per-floor room pointer tables, and the
    `maps/map_FF_R.bin` filenames used by the runtime loader. It omits
    floor/room combinations for which stage 06 imported no cells.

  - `build_99_asm_assemble.py` performs no floor or room transformation. It
    assembles `src/asm/wolf3d.asm`; through that source's includes, the
    application consumes the stage-91c-generated tables in
    `src/asm/maps.asm`. The individual room binaries remain external runtime
    files under `tgt/maps`.

  Existing assembly navigation trace:

  - `src/asm/wolf3d.asm` starts a new game by clearing the ten bytes of
    `room_flags`, selecting floor 0 and room 0, calling `map_load`, and then
    calling `plyr_init`. `map_load` already initializes the room's sprites, so
    the additional `map_init_sprites` call presently made by `new_game` is
    redundant.

  - `src/asm/player.asm` owns `cur_floor`, `cur_room`, `from_floor`,
    `from_room`, `cur_x`, `cur_y`, and `orientation`. `plyr_init` calls
    `get_floor_start`, which scans room 0 for the `cell_is_start` bit, places
    the player on that cell, and initially faces north.

  - Each main-loop iteration calls `plyr_input`. Movement keys produce
    camera-relative x/y velocity, rotation updates the four-way orientation,
    and `trans_dx_dy` converts the requested movement into map-relative
    coordinates. `get_cell_from_coords` wraps both coordinates modulo 16 and
    returns the target cell's four-byte record from `cell_status`.

  - The movement collision path first refuses cells marked as walls. It then
    tests `cell_is_to_room` and jumps directly to `change_room`; otherwise it
    commits the requested coordinate change. The generic `cell_is_blocking`,
    `cell_is_trigger`, and ordinary `cell_is_door` flags are not consulted by
    this movement path. The linked-room tiles work because their catalog
    records are triggers but are not marked as walls.

  - `src/asm/maps.asm:map_load` uses `cur_floor` to index `floors`, then
    `cur_room` to index that floor's room table. It asks MOS to load 8 KiB from
    the selected `maps/map_FF_R.bin` into `cell_status` at `0xB7E000`, then
    rebuilds the active sprite table from the loaded cell records.

  - `change_room` marks the departing room as visited, records it in
    `from_room`, and derives the destination room by subtracting 30 from the
    linked-door object ID. Before leaving, it copies the complete active 8 KiB
    room image into one of ten fixed 8 KiB backing areas at
    `0x0A0000`–`0x0B3FFF`. An unvisited destination is loaded from disk; a
    visited destination is restored from its backing area. This preserves
    mutated cell and sprite state separately for each room on the current
    floor.

  - Arrival currently relies on the reciprocal-door convention. After
    entering the destination room, `change_room` converts `from_room` back to
    object ID 30–39 and `get_room_start` scans for a cell carrying that object
    ID. This is why each connected room needs the matching door back to the
    room just departed.

  - The current arrival implementation sets `cur_x`/`cur_y` to the reciprocal
    door cell itself. It does not select the intended adjacent cell, inspect
    the door's eight neighbors, update the player's facing direction, or
    update `cur_cell`. `get_room_start` also has no 256-cell termination or
    failure return, so a missing reciprocal door causes an endless scan.
    Multiple matching doors are not detected; the first one wins.

    Placing the player on the destination door may be intentional rather than
    merely unfinished. Earlier experimentation apparently advanced the player
    automatically one cell beyond a door, but that behavior was rejected
    because it removed control from the player and could force an undesirable
    move. Door-cell occupancy can instead serve as a temporary transition
    state, provided it receives explicit handling. From that state the player
    must be able either to proceed into the newly loaded room or immediately
    reverse the transition—by turning around and moving back or by backing
    away—without becoming trapped, entering an invalid cell, or accidentally
    bouncing repeatedly between rooms. The present movement code only tests
    the cell being entered, not the door cell currently occupied, so this
    immediate-reversal behavior is not presently explicit and must be
    recovered or designed before changing arrival placement.

  - The room-state system is floor-local only in its present form. There is
    one ten-byte `room_flags` array and one set of ten backing addresses;
    `from_floor` is declared but unused, and `change_room` never changes
    `cur_floor`. A genuine transition between floors will require an explicit
    policy for resetting, discarding, or separately preserving the departing
    floor's cached room state.

  - Generated room filename tables are indexed directly by numeric room ID,
    but stage 91c emits entries only for rooms that exist. Therefore room IDs
    must currently be dense from zero through the highest room number. A gap
    in the authored room sequence would make direct indexing select the wrong
    pointer or run beyond the table.

- [ ] Separate the concerns currently combined in `src/asm/maps.asm`.

  - Keep general map representation and runtime operations together:
    constants, record layout, coordinate/cell lookup, room-file loading,
    sprite-table initialization, and start-cell searches.
  - Move room-navigation policy and mutable room caching into a dedicated
    `room_transition.asm`: `room_transition_depart`, `change_room`,
    `room_flags`, the visited flag, room-state backing-address tables, and the
    linked-room object-ID lookup.
  - Keep the persistent player-facing transition variables in `player.asm`.
  - Move `start_obj_id`, floor/room pointer tables, and room filenames into a
    generated-only `maps_generated.asm`.
  - Change `build_91c_asm_map_masks.py` to replace the generated file as a
    whole instead of locating a marker and rewriting the tail of handwritten
    assembly. This should keep generated test-map changes out of handwritten
    code reviews and commits.
  - Avoid splitting map-coordinate helpers, loading, and sprite
    initialization into additional tiny files unless a concrete maintenance
    problem justifies it.
